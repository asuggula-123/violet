# Violet — architecture (v1)

Each person gets a personal AI agent called **Violet**, reachable at its own chat
address. Owners text their agent. Agents talk to each other to sort things out.
Humans approve every outcome.

This document is the build contract. Code and tests refer to the invariant IDs
(`I1`…`I20`) below. If the code and this document disagree, fix one of them in
the same commit.

---

## 1. Decisions already made

| Topic | Decision |
|---|---|
| Transport | **Telegram Bot API** (one bot per agent). WhatsApp is blocked for this use: Meta's WhatsApp Business Solution Terms bar general-purpose AI assistants as a number's primary function (in force since 15 Jan 2026 outside the EEA/Italy/Brazil). Twilio WhatsApp inherits the same terms. The transport is an interface, so WhatsApp can be added later. |
| Agent-to-agent | **Open conversation** between LLMs, not a fixed times-only protocol. Safety comes from structure (section 2), not from restricting topics. |
| Strangers | Fixed canned reply. No model call. |
| Stack | TypeScript (strict, ESM), Node 22, Postgres 16, Fastify, Claude API. Deploy target Fly. |
| Model | `VIOLET_MODEL`; the default is the one model id in `src/config.ts`. |

## 2. Principles

1. **Rules live in code, not in the prompt.** Every rule in the spec is enforced
   by a code path that holds even if the model is fully compromised. Prompts are
   a second layer, never the only one.
2. **Open mouth, closed vault.** Each agent has two minds:
   - **Brain** — serves the owner thread. Full access (calendar, Gmail, notes,
     history). Takes instructions only from the owner.
   - **Envoy** — talks to other agents. It knows only (a) the *brief* its owner
     released for this conversation, (b) its owner's free/busy inside the
     conversation's time window, (c) the conversation transcript. It has no
     tool, no context and no code path that reaches event details, email,
     notes or the owner thread. Whatever a hostile agent talks it into, there
     is nothing in the vault to spill.
3. **Untrusted text is data.** Anything not typed by the owner in the owner
   thread (strangers, other agents, email bodies, calendar invites) is wrapped
   and labelled before any model sees it, and never reaches a model as an
   instruction turn.
4. **One door out.** Every outbound message goes through `OutboundGateway`.
   Pause, logging and "who may receive what" are enforced there.
5. **Humans approve outcomes.** Approval text is rendered by code from
   structured data. Only a real inbound owner message can resolve an approval.
   **What you see is what gets booked:** every text field written to a calendar
   appears in full in the prompt the owner answers (stored in the form the prompt
   shows; NUL dropped and lone surrogates as U+FFFD, which `jsonb` rejects), with the full date and time (`exactRange`); what does not fit is refused,
   never cut. CalendarWriter checks it again before writing: a title or location
   missing from the stored prompt (a row stored before this rule) is not booked.
6. **Everything is logged.** `action_log` is append-only.

## 3. Hard invariants

| ID | Invariant |
|---|---|
| I1 | Owner identity = exact match of `(transport, fromAddress)` with the agent's `owner_address`. Nothing in message content can grant owner authority. |
| I2 | Only owner-thread inbound messages become instruction (`user`) turns for the Brain. |
| I3 | A non-owner sender never triggers a model call. They get one canned reply (rate-limited) that says it is an AI, takes the message, and reveals nothing — not even the owner's name. |
| I4 | `OutboundGateway` exposes exactly two ways out: `sendToOwner(agentId, text, …)` and `sendCanned(agentId, contactId, cannedKey)`. There is no API that sends free text to a non-owner. |
| I5 | The model cannot approve. Approvals are resolved only by the deterministic resolver acting on an inbound owner-thread message (typed yes/no or a button press). No tool resolves approvals. |
| I6 | Calendar writes happen only inside `CalendarWriter`, which loads the approval from the DB, requires status `approved`, and builds the event from the **stored approval payload**, never from caller arguments. |
| I7 | An agent-to-agent outcome is booked only when **both** owners' approvals for that exact proposal are `approved`. Free/busy is re-checked right before booking. |
| I8 | No code path sends email. `GmailProvider` has no send method. The real Gmail HTTP client allow-lists method+path and rejects anything else (in particular `messages/send` and `drafts/send`). |
| I9 | The Envoy's tool set is exactly: `check_availability`, `say`, `propose`, `accept`, `decline`, `ask_owner`, `end_conversation`. Its context is built only from a2a tables. Unknown tool names are rejected. |
| I10 | `check_availability` returns busy intervals only (start/end). It is limited to the conversation's window (≤ 7 days for a window declared by the peer, ≤ 31 days for one set by the own owner), and to a per-side call budget. No window → no availability access. |
| I11 | Everything the Brain releases to another agent (brief, later guidance) passes `EgressGuard` (blocks private calendar phrases the owner did not use themselves) and the **taint rule**: if the turn is tainted (the Brain read untrusted content in it, or its history or context holds third-party text), the release is held for the owner's yes (I20). The owner is always shown, in code-rendered text, exactly what was released. |
| I12 | Peer agents must be in the same household. Limits per pair: open conversations ≤ 3, new conversations per day ≤ 10, messages per side per conversation ≤ 12, `ask_owner` per side per conversation ≤ 2. |
| I13 | Text authored by another agent or a stranger is sanitized (control chars and newlines stripped, length capped) and quoted before it is shown to an owner. It can never forge a second line; folding makes it harder to mistake for an approval prompt (best effort, 8.2), and a look-alike prompt can resolve nothing (I5). |
| I14 | Paused agent: the gateway refuses every send except the single pause/resume ack. The router stores inbound (and, for strangers, raises the `message_taken` digest flag, which sends nothing) and does nothing else; a message once held stays held on every retry of its job, even after a resume. The scheduler skips the agent. The Envoy does not run. Nothing from the agent reaches another agent, also from a Brain turn already running when the pause lands: opening, guidance and an owner's close are refused inside the transaction that would write them (8.6), the other side's accept does not read the paused owner's free/busy, and a booking both owners said yes to waits (the paused owner's calendar is neither read nor written) until the resume. |
| I15 | Every inbound, outbound, suppressed send, model turn, tool call, denied tool call, approval change, calendar write, draft, a2a message, flag, digest, pause/resume and pairing writes an `action_log` row. A DB trigger blocks UPDATE/DELETE/TRUNCATE on `action_log`. A text the transport delivered always leaves `outbound.sent`, with `recorded: false` when its `messages` row could not be stored, and is never sent again by a retry (if the action log itself cannot be written either, the miss goes to the error log and the text is still not resent); the log makes NUL and lone surrogates in a detail storable; a job attempt that fails and is rescheduled leaves `job.retry`. |
| I16 | Secrets come from env vars only. Google refresh tokens are encrypted at rest (AES-256-GCM, key from env). Nothing secret is logged. |
| I17 | Immediate texts to an owner are only: replies to their own message, approval prompts, Envoy questions, a2a notices (8.4: `Talking to …`, `Told …`, `Waiting for …`, `Booked: …`, `… said no to: …`, `No answer from …`, booking failures; bounded by the I12 limits; sent at once, also in quiet hours, outside the daily budget), and urgent flags. Urgent non-approval flags are budgeted (≤ 3 per local day) and respect quiet hours (22:00–07:00 owner time). Everything else waits for the digest. |
| I18 | Webhooks are authenticated (Telegram secret token, constant-time compare) and idempotent (unique transport message id). |
| I19 | A typed yes or no counts only directly under the real prompt. Every `approval.approved` / `approval.denied` with `via: 'text'` was either a transport reply-to on a genuine delivery of that approval, or written with a genuine delivery of that approval in RUN(m) — and for a bare answer that approval was the only approval in RUN(m) (and pending). A genuine delivery is a row of `approval_deliveries`, nothing else (never text, purpose or buttons); "directly above" is the transport's own chat numbering, never stored row order (8.3). Safety does not depend on what any text looks like. |
| I20 | In a tainted Brain turn, nothing from the owner's side reaches another agent without the owner's yes on exactly what crosses: every release (`talk_to_agent`, `tell_envoy`) is held as an `a2a_release` approval whose prompt shows every value sent (topic, the time window to the minute — stored to the minute too, with the year and UTC offset shown whenever they are not otherwise certain — and the exact text), whoever wrote the words. Code cannot tell what the owner meant to keep private ("don't tell Sam, but …"), so it does not try. |

## 4. Stack and conventions

- Node 22, TypeScript `strict`, ESM (`"type": "module"`), `tsx` for dev, `tsc` build to `dist/`.
- Runtime deps: `fastify`, `pg`, `@electric-sql/pglite`, `zod`, `luxon`, `@anthropic-ai/sdk`, `pino`. Keep the list short; justify anything else.
- No ORM. SQL lives in repo modules. Migrations are plain `.sql` files run in order.
- **Db adapter**: one interface, two drivers. `PgDb` (node-postgres) for real Postgres. `PgliteDb` (Postgres compiled to WASM, in-process) for zero-setup tests, the demo, and local dev when `DATABASE_URL` is unset. Driver differences are hidden in the adapter: never read `bigint` columns raw (cast `::int` / `::text` in SQL), always `count(*)::int`.
- IDs: `crypto.randomUUID()` stored as `text`. Times: `timestamptz`. No `Date.now()` in app code — everything takes a `Clock`.
- Tests: `vitest`. Default driver PGlite in-memory. If `TEST_DATABASE_URL` is set, each test world creates and drops its own schema in real Postgres. Both must pass.
- Scripts: `npm run build` (tsc to `dist/`, copies the `.sql` migrations), `npm run typecheck`, `npm test`, `npm run test:pg`, `npm run test:e2e`, `npm run migrate`, `npm run dev`, `npm run demo`, `npm run owner:add`, `npm run google:link`, `npm run pairing:reissue`. The CLIs also run from the build with no dev dependency: `npm run migrate:prod`, `owner:add:prod`, `google:link:prod`, `pairing:reissue:prod`, `demo:prod` (`node dist/cli/<name>.js`).
- Test personas are **Alex** and **Sam**. No real names, numbers, emails or keys anywhere in the repo.
- `.gitignore`: `node_modules`, `dist`, `.env*` (except `.env.example`), `.data`, `.worktrees`.

## 6. Data model

Migration files are pre-assigned so parallel milestones never collide.

**001_core.sql (M1)**

`messages`, `jobs`, `flags` and `contact_notes` also have `seq bigserial unique`: a stable order for
rows written at the same clock instant (the FakeClock makes that common). Order by `seq`; never read it raw.
- `households(id, name, created_at)`
- `owners(id, household_id, name, timezone, digest_hour default 18, created_at)`
- `agents(id, owner_id unique, name default 'Violet', transport, agent_address, owner_address null, pairing_code_hash null, pairing_expires_at null, paused bool, paused_at null, created_at, unique(transport, agent_address))`
- `contacts(id, agent_id, transport, address, display_name null, kind 'owner'|'stranger', first_seen_at, last_seen_at, last_canned_reply_at null, unique(agent_id, transport, address))`
- `contact_notes(id, agent_id, contact_id null, subject null, body, created_at)`
- `messages(id, agent_id, thread 'owner'|'contact', contact_id null, direction 'in'|'out', body, purpose null, transport_message_id null, reply_to_transport_message_id null, meta jsonb, created_at)`
- `inbound_events(id, transport, transport_message_id, agent_address, payload jsonb, received_at, processed_at null, progress jsonb default '{}', unique(transport, transport_message_id))`; M2 (002) adds `arrival_seq bigserial` (arrival order at ingest, used by the approval resolver) — `progress` maps each routing step already done to its result, so a retried `inbound.process` job resumes instead of redoing side effects.
- `jobs(id, type, lane null, payload jsonb, status 'queued'|'running'|'done'|'failed'|'dead', attempts, max_attempts, run_at, locked_at null, last_error null, dedupe_key unique null, created_at, finished_at null)` — `failed` = waiting for a retry at `run_at`; `dead` = out of attempts. A partial unique index on `lane where status = 'running'` makes "one running job per lane" a database rule. `dedupe_key` is unique for the table's lifetime (an idempotency key, not "one active job"). A lane runs in order: a job is claimable only while **no older unfinished job of its lane** exists — `queued` and due, `failed` (waiting for a retry) or `running` — whatever row locks other workers hold (a head job another worker has locked but not yet marked running still holds the lane). A `queued` job scheduled for later takes its place in the lane when it becomes due. **Visibility timeout:** every pump first recovers jobs still `running` after `staleMs` (default 10 min, measured on the `Clock` from `locked_at`): one that used its last attempt becomes `dead` (+ `job.dead`), any other is requeued as `failed`, due now. So a crashed worker or a finish that could not be written never wedges a lane, and handlers run **at least once**. An attempt's outcome is written only if the row still carries that attempt number, so a late finish from a lost worker is a no-op. `job.dead` rows carry `agent_id` when the lane is an agent id. Every attempt that fails and is rescheduled (a handler error, or a stale requeue) writes `job.retry {jobId, type, lane, attempt, error}` in the same transaction, `error` = the error class and code only (`LlmError:rate_limited`, `stale`), never its message. A handler error with `permanent: true` (e.g. `PermanentTransportError`) makes the job `dead` at once; one with `retryAfterMs` is not retried before that delay.
- `flags(id, agent_id, kind, urgency 'now'|'digest', text, dedupe_key null, status 'pending'|'sent'|'suppressed', created_at, delivered_at null, digest_date null, unique(agent_id, dedupe_key))`
- `scheduler_state(name, scope, last_run_at, primary key(name, scope))`
- `action_log(id bigserial, at, agent_id null, actor, action, detail jsonb)` + append-only trigger
- `schema_migrations(version, applied_at)` — `migrate()` is safe to run from several processes at once (every instance migrates at boot): each script takes a transaction-level advisory lock on the schema and inserts its version row first, so the loser of a race rolls back and skips.

**002_approvals.sql (M2)**
- `approvals(id, agent_id, ref int, kind, payload jsonb, prompt, status 'pending'|'approved'|'denied'|'expired'|'cancelled'|'executed'|'failed', group_id null, prompt_transport_message_id null, prompt_sending_until null, idempotency_key null, created_at, expires_at, resolved_at null, resolved_by_message_id null, executed_at null, error null, unique(agent_id, ref), unique(agent_id, idempotency_key))` — `prompt_transport_message_id` null = prompt not delivered yet (paused or send failed).

**004_a2a.sql (M4)**
- `a2a_conversations(id, household_id, initiator_agent_id, responder_agent_id, topic, status 'open'|'awaiting_approval'|'closed', window_start null, window_end null, last_seq int, live_proposal_seq null, accepted_proposal_seq null, outcome_group_id null, outcome_state null|'booking'|'booked'|'failed', outcome_claimed_until null, outcome_claimed_by null, open_key unique, created_at, updated_at, closed_at null, close_reason null)` — `last_seq` is bumped under the row lock to number messages; `open_key` = the release's idempotency key.

Owner guidance is stored as private `guidance` messages (not on the side row).

- `a2a_turns(turn_key pk, conversation_id, agent_id, trigger_seq, status 'running'|'waiting'|'done', requeues, outcome null, created_at, finished_at null)` — one Envoy turn per delivery; `waiting` = paused, re-queued by onResume.

**005_flags.sql (M5)**
- `flags` gains `held_until null` (held for quiet hours), `budget_date date null` (owner-local date whose budget it uses), `attempt_at null` (send lease), `overflowed_at null` (a `now` flag turned digest item), `digest_id null` (the one digest carrying it), `retry_at null` + `send_failures` (release-task backoff after a retryable send failure). - `digests(id, agent_id, local_date, body null, status 'sending'|'sent'|'empty'|'rolled_over', item_count, left_out, created_at, lease_until null, sent_at null, send_failures, unique(agent_id, local_date))` — a row closes the date; `body` null = empty.

**006_transport.sql (M6)** — `telegram_state(bot_id pk, last_update_id)`

**007_i19.sql (I19)**
- `approval_deliveries(id, seq, agent_id, approval_id, kind 'prompt'|'reprompt'|'which_one', transport_message_id null, for_message_id null, created_at, unique(for_message_id, approval_id))`, unique `(agent_id, transport_message_id)` where sent, one `prompt` row per approval. One row per message the approvals service itself sent as the prompt of ONE approval. `transport_message_id` NULL = claimed, not (yet) sent; `for_message_id` = the owner message that caused a re-prompt / which-one (NULL for the first delivery). Backfilled from `approvals.prompt_transport_message_id`.
- `approvals` gains `hold_until null` and `turn_message_id null`: an approval requested inside a Brain turn is held until the turn delivers it (8.2).

**008_approval_taint.sql (P4)**
- `approvals` gains `tainted boolean default false`: requested inside a tainted Brain turn (8.2). Approvals still pending when the migration runs are set `true` (fail closed).

## 7. Contracts

These are the starting contracts. M1 creates them as real `.ts` files. A later
milestone may change one if it must — keep the change minimal and report it.

```ts
// src/db/db.ts
export interface Queryable {
  query<T = Record<string, unknown>>(sql: string, params?: unknown[]): Promise<{ rows: T[]; rowCount: number }>;
}
export interface Db extends Queryable {
  tx<T>(fn: (tx: Queryable) => Promise<T>): Promise<T>;
  exec(sql: string): Promise<void>;   // multi-statement script, no params (migrations; runs atomically)
  close(): Promise<void>;
}

// src/clock.ts
export interface Clock { now(): Date }

// src/transport/types.ts
export type TransportName = 'fake' | 'telegram';
export interface InboundMessage {
  transport: TransportName;
  agentAddress: string;              // which agent endpoint received it
  fromAddress: string;               // sender's stable id on this transport
  fromName?: string;                 // display name — untrusted
  kind: 'text' | 'button' | 'unsupported';
  text: string;                      // '' when unsupported
  buttonPayload?: string;            // e.g. "approve:<approvalId>"
  transportMessageId: string;        // unique per transport — idempotency key
  replyToTransportMessageId?: string;
  chatMessageId?: string;            // (I19) '<chat>:<n>': this message's number in its chat; absent = unknown
  receivedAt: Date;
}
export type OutboundPurpose = 'reply' | 'approval' | 'question' | 'flag' | 'digest' | 'ack' | 'canned' | 'transcript';
export interface OutboundMessage {
  agentAddress: string;
  toAddress: string;
  text: string;
  buttons?: { id: string; label: string }[];
  purpose: OutboundPurpose;
}
export interface Transport {
  readonly name: TransportName;
  send(msg: OutboundMessage): Promise<{ transportMessageId: string }>;   // '<chat>:<n>' (multi-part: the last part)
  numberInbound?(msg: InboundMessage): string | undefined;              // (I19) test transports only: app.ingest numbers unnumbered inbound
}
// I19 transport contract: in a chat every message, in either direction, takes the next number.
// chatOrder.ts isDirectlyAbove(outboundId, chatMessageId): same chat and n(m) = n(out) + 1 (BigInt);
// unknown, malformed, another chat or any gap → false. FakeTransport({ numbering: 'per-chat' (default)
// | 'per-bot' | 'none' }) numbers both directions; skip(agent, address, n) simulates a gap.
// send() failures: TransportError { permanent, reason, retryAfterMs? }, subclassed as
// PermanentTransportError (retrying cannot help) and RetryableTransportError.

// src/core/outbound.ts
export interface OutboundGateway {
  /** Returns null when suppressed (paused). `meta.tainted` (M4) is stored on the message row (K1, section 8.2).
   *  Every text is made storable first (U+0000 dropped, lone surrogates → U+FFFD). A storage failure after a
   *  successful send writes outbound.sent `recorded: false` and returns `messageId: null` (no rethrow, no resend). */
  sendToOwner(agentId: string, text: string, opts: { purpose: Exclude<OutboundPurpose, 'canned'>; buttons?: { id: string; label: string }[]; meta?: { tainted?: boolean; from?: 'brain' } }): Promise<{ messageId: string | null; transportMessageId: string } | null>;
  // meta.from 'brain' (I19): a reply the Brain wrote, stored on the row.
  sendCanned(agentId: string, contactId: string, key: CannedKey): Promise<void>;
}
// createOutbound() also returns a ControlChannel { sendPauseAck } that only the router
// receives: the single pause/resume ack (I14) is not reachable through the gateway.

// src/llm/types.ts — mirrors the Anthropic Messages API shape
export type LlmBlock =
  | { type: 'text'; text: string }
  | { type: 'tool_use'; id: string; name: string; input: Record<string, unknown> }
  | { type: 'tool_result'; tool_use_id: string; content: string; is_error?: boolean }
  | { type: string; [k: string]: unknown };          // thinking etc. — pass back verbatim
export interface LlmMessage { role: 'user' | 'assistant'; content: string | LlmBlock[] }
export interface LlmTool { name: string; description: string; input_schema: Record<string, unknown> }
export interface LlmRequest {
  system: string;                    // stable: cached (prompt caching), byte-identical across turns
  systemDynamic?: string;            // volatile (time, pending items): sent after the cache breakpoint
  messages: LlmMessage[]; tools: LlmTool[]; maxTokens: number;
  /** Not sent to the API. Used for logging and for scripting tests. */
  meta: { agentId: string; mind: 'brain' | 'envoy'; conversationId?: string };
```

### Google (M3)

- `src/google/http.ts` is the only code that calls Google. The allow-list (`allowlist.ts`, I8) is checked on the parsed URL before `fetch`: exact host, exact path segments (raw path must be in normal form: no `%`, `\`, dot or empty segments), ids `[A-Za-z0-9_-]`, and a per-route list of query keys (`sendUpdates` is pinned to `none`, every value). Providers `encodeURIComponent` ids in paths, so a hostile id is denied by the allow-list rather than reshaping the URL. Allowed: `POST oauth2…/token`, `POST calendar/v3/freeBusy`, `GET|POST calendar/v3/calendars/primary/events`, `DELETE …/events/{id}`, `GET gmail/v1/users/me/{profile, messages, messages/{id}, threads/{id}}`, `POST …/me/drafts`. A denied call throws `GoogleDeniedError` and writes `google.denied` (best effort, never masking the denial; control characters and lone surrogates in the logged URL are escaped so jsonb accepts it). No retries in the client (the job queue retries); one bounded re-try after a 401 with a fresh token.
- Typed errors (`errors.ts`), each with a short owner-safe `safeMessage`, also exposed as `ownerMessage` (what the tool loop and `CalendarWriter` show, so a missing connection, revoked access or a missing scope is named; texts never offer a connect link the Brain cannot make): `GoogleDeniedError`, `GoogleNotConnectedError`, `GoogleAuthError` (401, `invalid_grant`, revoked), `GoogleScopeMissingError` (with `capability`), `GoogleNotFoundError`, `GoogleConflictError`, `GoogleRateLimitedError` (`retryAfterSec`), `GoogleTransientError`, `GoogleInvalidInputError`, `GoogleRequestError`. `retryable` is true for rate-limited and transient.
- Capabilities come from the **granted** scopes: `calendarFreeBusy`, `calendarRead`, `calendarWrite`, `gmailRead`, `gmailDraft`. A call without its capability throws `GoogleScopeMissingError` before any network call. Default scopes: `calendar.freebusy`, `calendar.events.owned`, `gmail.readonly`, `gmail.drafts.create` (`GOOGLE_SCOPES` overrides).
- `invalid_grant` on refresh → `revoked_at` set, `google.revoked` logged, one `now` flag `Google access expired — reconnect needed.` (dedupe key per connection), `GoogleAuthError`. A refresh token that fails to decrypt (wrong/rotated `TOKEN_ENC_KEY`, corrupt row) → `GoogleAuthError` reason `undecryptable`, one `now` flag of kind `google.undecryptable` (same text, dedupe per connection), the account is **not** marked revoked (restoring the key recovers it). `googleModule` (in `defaultModules`) binds `app.flags` for this.
- Connect: `oauth.createConnectLink(ownerId)` (CLI `npm run google:link -- --owner <id>`) → `GET /oauth/google/start?state=…` → Google consent → `GET /oauth/google/callback` → `google.connected` (or `google.connect_failed {reason}`). Routes exist only when Google is configured. `createDeps` → `createGoogleProviders` (`providers.ts`) uses the real providers when `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `GOOGLE_REDIRECT_URI` and `TOKEN_ENC_KEY` are all set. Otherwise, with `NODE_ENV=production` **or a transport that reaches real people** (`TRANSPORT=telegram`, whatever `NODE_ENV` is: a real owner is never told "Booked" on a stand-in), it uses `UnconfiguredCalendar` / `UnconfiguredGmail` (`unconfigured.ts`, one boot warning): every call throws `GoogleNotConfiguredError` (code `not_connected`, not retryable, `ownerMessage` "Google isn't connected on this server", which the tool loop and `CalendarWriter` show), nothing is stored — so Brain calendar/Gmail tools return that tool error (`read_email` too: it passes a typed `GoogleError`'s `ownerMessage` through and keeps its fixed "I couldn't open that email." for anything else), an approved `calendar_event` ends `failed` with `I couldn't book #n: Google isn't connected on this server.` and no `booked` flag (its `calendar_writes` intent row is undone: `deleted_at` set, no event id, no `calendar.event_*` log), and the conflict check logs one line per scheduler run (not per agent). Only with the fake transport outside production (tests, the demo, local dev without real bots) the in-memory fakes, with one info line at start-up. `googleOf(deps)` returns the services behind real providers (null otherwise, so no `/oauth` routes).
- Calendar: `createEvent` uses event id = lowercase base32hex(sha256(idempotencyKey)) and `sendUpdates=none`; HTTP 409 returns the same id. `deleteEvent` treats 404/410 as done. `listEvents` skips cancelled events and reads at most 20 pages of 250; more pages left at that point is a `GoogleRequestError`, never a partial list; all-day dates start at the first instant of that date in the calendar's zone (midnight, or the DST transition where midnight is skipped; end exclusive), `allDay: true`. Floating wall times inside a DST gap resolve forward (pre-transition offset), overlaps take the earlier instant.
- Gmail: `search` caps at 25 messages; bodies prefer `text/plain`, fall back to stripped HTML, capped at 20,000 chars. Sender-controlled input is bounded: each part's base64 is cut before decoding, the MIME tree is walked iteratively (depth ≤ 50, ≤ 500 parts, the rest ignored), HTML is cut at 80,000 chars and stripped in one linear scan (no backtracking regex; an unclosed tag, comment or script runs to the end and is dropped). Drafts are hand-built RFC 2822 (base64 UTF-8 body, RFC 2047 subject); recipients must be bare addresses within RFC 5321 limits (address ≤ 254, domain ≤ 253 chars) and the subject has no control characters (`GoogleInvalidInputError`). Replies set `threadId`, `In-Reply-To`, `References` (the first id plus the last 10). `To` and `References` are folded (CRLF + space) so no line exceeds ~78 chars (RFC 5322 limit 998). No send anywhere; a test scans `src/` for send endpoints.

### Telegram transport (M6)

- One bot per agent. `agent_address` = bot id (the digits before `:` in the token); owner address = Telegram user id. Tokens come from `TELEGRAM_BOT_TOKENS` (comma-separated, format-checked, no duplicates).
- Ids: inbound `transportMessageId` = `<bot id>:<update id>` (I18). Outbound ids, `replyToTransportMessageId` (a reply, or the message carrying a pressed button) and an inbound message's `chatMessageId` (I19) = `<chat id>:<message id>`.
- **Numbering (I19), not verified against live Telegram** (no network where this was built): typed yes/no relies on Telegram giving every message of a private chat, in either direction, the next `message_id`. If that is off, typed answers fail closed (Violet shows the prompt again); reply-to and the buttons still work. If Telegram numbered all of a bot's chats together, a stranger's message between prompt and answer would be a gap: the same fail-closed case (tested with `FakeTransport({ numbering: 'per-bot' })`).
- Inbound: private chats only. Text → `text`; other messages → `unsupported`, and so is text the sender did not type (a forward: `forward_origin`/`forward_from`/`forward_from_chat`/`forward_sender_name`/`forward_date`, or `via_bot` output), so it never reads as the owner's words (principle 3, I5); `callback_query` → `button` (`buttonPayload` = callback data, `text` '', sender = the presser). Edits, channel posts, bot senders, other updates → ignored. Group/supergroup/channel → ignored and the bot leaves the chat. Untrusted strings (text, names, callback data) drop U+0000 and replace lone surrogates with U+FFFD, which Postgres `jsonb` rejects, so no update is unstorable (a webhook 500 on every redelivery, a stuck poll offset). Every ignored update is logged as `inbound.dropped` (`transport`, `botId`, `updateId`, `reason`) and a left chat as `telegram.chat_left` (I15).
- Outbound: plain text (no `parse_mode`), link previews off, split at 4096 UTF-16 units on paragraph/line/space boundaries; buttons = one inline-keyboard row on the last chunk, `callback_data` = button id (≤ 64 bytes, else a permanent error). A retryable failure after some chunks went out is remembered in process (6 h on the app `Clock`), keyed by the running job's id (`core/jobContext.ts`: the job queue runs each handler inside `runInJob(job.id, …)`) and the message, so only that job's retry resumes with the first undelivered chunk; a new job, or a send outside any job, always sends the whole message.
- Errors: 400/401/403/404 → permanent; 429 (with `retry_after` → `retryAfterMs`), 5xx, network → retryable. The token is in the request URL, so errors are built from the method name and Telegram's `error_code`/`description` only; URLs and fetch errors are never logged.
- Webhook mode: `POST /webhooks/telegram/:botId`, `X-Telegram-Bot-Api-Secret-Token` checked against `TELEGRAM_WEBHOOK_SECRET` (constant time) before the body is parsed → 401; unknown bot → 404; malformed body → 400; else ingest → 200. Error bodies are `{"ok":false}`. At boot, with `PUBLIC_BASE_URL`, `setWebhook` per bot (secret token, `allowed_updates` = message, callback_query).
- Polling mode (`TELEGRAM_MODE=polling`, local dev): per bot, `deleteWebhook` once, then long-poll `getUpdates`; the offset (`telegram_state`, with the time of the last ingested update) advances only after an update is ingested. An offset over 6 days old is not sent (Telegram may restart update ids at a random lower value after a week without updates); the stored id then follows the new ids down, and redeliveries are deduplicated by ingest.
- `owner:add --transport telegram [--bot-username <name>]` prints the exact `/start <code>` text and a `t.me/<bot>?start=<code>` link.

## 8. Flows

### 8.1 Inbound routing (deterministic, before any model)

1. Webhook authenticates, normalizes to `InboundMessage`, calls `app.ingest` → insert `inbound_events` (dedupe) + enqueue `inbound.process` on lane = agent, in one transaction (a failed enqueue rolls back the insert, so a redelivery is not mistaken for a duplicate) → return 200. **Pause is immediate:** if the sender is the owner (I1) and the text is exactly `pause` / `resume` (rule of step 4), the same transaction locks the agent row (`SELECT … FOR UPDATE`, also when the command changes nothing), flips `agents.paused` if it differs, writes `agent.paused` / `agent.resumed` and records the `pause.state` step in `progress`. Because every pause/resume command serializes on that row lock, concurrent commands enqueue their jobs in flip order and the last ack always matches the final state. Any other message that arrives while the agent is paused gets the `paused_at_arrival` step recorded. A redelivery inserts nothing, so it flips nothing.
2. Unknown `agentAddress` → log, drop.
3. Pairing: if the agent has no `owner_address` and the text is `/start <code>` matching the unexpired pairing code → bind owner, ack. A wrong or missing code is treated like any stranger. `reissuePairingCode` (`core/pairingReissue.ts`, CLI `pairing:reissue -- --agent <id> [--reset]`) replaces the code of an unpaired agent in one transaction under the agent row lock (same generator, hash and 24 h expiry; the old code stops matching; `pairing.code_issued {expiresAt, reissued, replaced: none|active|expired}`); a paired agent is refused unless `--reset`, which first clears `owner_address` and demotes that contact to `stranger` (`pairing.reset`), so the old chat is a stranger from its next message (I1). Neither the code nor its hash is logged. The router decides pairing, owner or stranger inside its `route` transaction from the agent row it locks there (`SELECT … FOR UPDATE`), and `app.ingest` locks the row before its owner/pause check, so a re-issue or reset that commits while a message is in flight is always seen: the old code never binds and the old chat is never routed as the owner. A reset that commits after `route` chose 'owner' (between steps, or before a retry) is caught by a fresh `isOwner` check at the start of `owner.handled`: the hooks are skipped and `inbound.dropped {reason: owner_reset}` is logged. A Brain turn already running when the reset commits finishes, but its reply is suppressed (`sendToOwner` reads `owner_address` at send time). Agent-to-agent after a reset (m4fix): the old chat, now a stranger, cannot answer the agent's pending approvals (typed or button) or Envoy questions, and reaches no model; a2a notices for the agent wait (`waiting`) while no chat is paired. The newly paired chat inherits the agent: open conversations and their Envoy questions (in the Brain's context), pending approvals (the old prompts are in the old chat, so never "above" a message of the new chat: a typed `yes 1` shows the prompt again in the new chat, and the yes under it answers it, I19), and the waiting notices, which the next `a2a.sweep` sends.
4. Sender is owner (I1):
   - `pause` / `resume` (exact, case-insensitive, optional leading `/`) → store the message, send the single ack (internal ack path), run `onPause` / `onResume`, in lane order. The state was already flipped at ingest (step 1); the job reuses that recorded result and never flips or logs a second time (it flips only if the sender became the owner after ingest, by a pairing earlier in the lane). An ack that fails permanently (owner blocked the bot; logged as `outbound.failed`) does not stop the hooks.
   - Paused → store, log (`inbound.held`), stop. Held = the agent is paused at processing time **or** was paused when the message arrived (`paused_at_arrival`). This includes messages that arrived before the pause but are processed after it, retries of older jobs, and messages that arrived while paused whose job runs after a later `resume` was ingested.
   - `ownerInterceptors` (approval resolver) → handled? stop.
   - `onOwnerMessage` (the Brain).
5. Sender is not owner (I3): upsert contact, store message, log. Raise a `digest` flag (`Message from “<name>”: “<text>”`, both quoted and folded with `quoteFolded` (8.2, K2), I13; it sends nothing). Paused (same held rule as step 4) → log `inbound.held`, raise that flag, stop: no canned reply, ever, for a held message, and the message is in the first digest after resume (8.6). Otherwise send the canned reply if none was sent to this contact in the last 12 h. The flag comes first so a canned reply that can never be delivered does not keep it back. The canned reply is **best-effort**: one attempt; every attempt leaves an outbound row (I15): a failure before or during the send is logged as `outbound.failed`, and a text that was delivered is logged as `outbound.sent` even if storing its `messages` row then fails (`recorded: false`). A failure never fails the job, retries or holds the lane.
6. Unsupported media: owner gets "I can only read text for now."; strangers get the normal canned flow.

Action names written by M1 (I15): `inbound.received`, `inbound.duplicate`, `inbound.dropped`, `inbound.held`,
`pairing.code_issued`, `pairing.bound`, `pairing.failed`, `pairing.reset`, `agent.paused`, `agent.resumed`, `outbound.sent`,
`outbound.suppressed`, `outbound.failed`, `canned.rate_limited`, `flag.raised`, `job.retry`, `job.dead`, `scheduler.failed`,

### 8.2 Owner turn (Brain)

System prompt (rules, owner profile, local time, pending approvals, open Envoy questions) + last 40 owner-thread messages + tool loop (≤ 10 steps). Final text → `gateway.sendToOwner(purpose 'reply')`. Tool results containing third-party text are wrapped in `<untrusted source="…">` and mark the turn **tainted**.

- Prompt: `system` = stable text (identity, owner name, rules, untrusted marking, time zone); `systemDynamic` = current local time + pending approval summaries.
- History: owner-thread rows up to and including the current message (I2: inbound = `user`, everything Violet sent = `assistant`), consecutive same-role rows merged, leading assistant rows dropped; the current message is the last user turn. **Hygiene (M4, K1):** outbound rows with purpose `flag`, `digest`, `transcript`, `question` replay as `[flag sent]`, `[daily digest sent]`, `[transcript sent]`, `[question from an agent conversation sent]` (details come from tools, which taint; Envoy questions come from the dynamic context). A row with `meta.tainted` (a reply written in a tainted turn, every delivery of an approval that is untrusted — its kind has `quotesThirdParty`, or `approvals.tainted`: it was requested in a tainted turn, P4 — and the resolver's reply for such an approval, an a2a line quoting an agent) replays wrapped as `<untrusted source="agent">` and makes the new turn start tainted. So text a tainted turn put into a prompt keeps its label even when the turn sent no reply. Pending untrusted approvals are listed wrapped (and taint) in `systemDynamic` and in `list_pending_approvals`; `Brain.contextProviders` sections are appended there and taint when they say so.
- **Appearance layer (best effort).** The reply neutralizer and the reserved line heads below reduce confusion between model-written and code-written text; they are not a guarantee, and no safety property rests on them. Visual similarity has no closed list (bidi reordering, new look-alikes, fonts), so the rules that matter are structural: approvals resolve only from a real owner message against a real pending approval and act on its stored payload (I5, I6, I7), and releases to another agent are held by code (I11, I20). What a fooled model can still do: say untrue things to its own owner in its own reply, including text that imitates Violet's notices or prompts (it can claim something was sent or booked, or show a fake question); it cannot make any of it happen.
- Reply neutralizer (K2, `reply.ts`, m4fix): decided by what is **not** a gap, so no list of blank glyphs is needed, and the tail is judged on the text as the owner sees it. (1) Cf and every `\p{Default_Ignorable_Code_Point}` are removed (the blank-rendering *letters* — Hangul fillers — are Default_Ignorable), except a ZWJ between two emoji, a variation selector after an emoji, and a ZWNJ (U+200C) between two Arabic-script letters (Persian spelling such as `می‌بینمت`, which would otherwise join wrongly; one-line `sanitize` paths still turn it into a space). (2) Each remaining code point, as written, is a **strong sign** (NFKC form contains `#`, or ♯ ⌗ ⋕ ⧣ ⩩ ▦ ▩ ╪ ╫ ╬ 井 丼 and the musical sharps U+1D130–U+1D132), a **weak sign** (any other non-Latin-1 `\p{S}` whose NFKC form has no letter, except currency, emoji, arrows, the Misc Symbols / Dingbats / Braille / Geometric Shapes / Misc Symbols and Arrows / Musical Symbols blocks and common math signs — fail closed: an unknown symbol may be a `#`), a **number** (`\p{N}`, or its NFKC form contains one: ⑦, ㏩), a **plain letter** (NFKD without marks is one ASCII letter: é, Ｂ; *digit-like* if that is I O l o), a **cjk letter** (Han/Hiragana/Katakana), another letter, a mark, or a **gap** (everything else: spaces, punctuation, U+2800 / U+1D159, private-use, unassigned, symbols whose NFKC form is letters such as Ⓡ, and every modifier letter `\p{Lm}` such as ʼ ˈ ˍ ꓸ ー, which read as punctuation; marks are gaps except inside a word). (3) Fail closed (m4fix round 2): a strong sign becomes `№` unless its next non-gap (signs skipped) begins a word of ≥ 2 plain letters, the first two not both digit-like, that ends at a gap, a sign or the end of the text (not at a number or another letter); 井 丼 also stay before a cjk letter (井戸, 牛丼です). So no list of digit-shaped letters is load-bearing: ʒ ȝ ɜ ƻ ɡ З after `#` fold because they are not plain letters. A weak sign whose next non-gap is a number becomes `№`. (4) NFKC (the mark `№` kept) and NFC. (5) On that normalized text, the letters of "reply yes or no" in order, with only gaps between any two of them, become "say yes or no"; letters are compared on a skeleton (NFKD, marks dropped, the confusables of r e p l y s o n from the Unicode data plus hand entries); a letter whose skeleton is still not ASCII (ɹ ǝ ŋ ɐ …) is a wildcard, at most 3 per match, so unlisted look-alikes fold while text in other scripts never matches; a non-letter that is such a confusable (`|`, `¥`) and the mark `№` (reads "No") are tried both as that letter and as a gap. (6) Steps 1–5 repeat until nothing changes, so the function is idempotent and nothing it normalizes (circled Ⓡⓔⓟⓛⓨ, squared letters) can rebuild the tail. **Right-to-left text:** when the text (or the fragment given to `quoteFolded` / `shown()`) contains any code point of the blocks Unicode reserves for right-to-left scripts (U+0590–U+08FF, U+FB1D–U+FDFF, U+FE70–U+FEFF, U+10800–U+10FFF, U+1E800–U+1EFFF; checked against the Script property: every Hebrew, Arabic, Syriac, Thaana, NKo, Adlam, … code point lies inside), every strong and weak sign folds, ASCII `#` included, whatever follows it — step 3 decides on logical order, which is the order the owner sees only when there is no right-to-left character and no bidi control (Cf, removed in step 1). So an owner who writes Hebrew or Arabic sees `#` as `№` in such messages (`נפגשים בשער #3` → `נפגשים בשער №3`). The ref fold makes a forged prompt harder to mistake for a real one; the tail fold is a second layer; neither is load-bearing. Not covered: a weak symbol (not a `#` look-alike) followed by a digit-shaped *letter*, and a tail with four or more look-alike letters outside the confusables data (the ref fold still holds). Owners see e.g. `#1 priority` → `№1 priority`, `#love` / `#lol` → `№love` / `№lol` (l o read as 1 0), `#a7` → `№a7`, `#straße` → `№straße`, `#東京` → `№東京` (any hashtag whose word is not plain Latin), a trailing `C#` → `C№`, `C♯7` → `C№7`, `⊕ 5` → `№ 5`, `reply yes or no to Sam` → `say yes or no to Sam`; `#friends`, `#café`, `#iPhone`, `C# is`, `井戸`, `★ 5`, `≤ 5` and other text only lose invisible characters and are NFKC-normalized. `quoteFolded(text, max)` folds, cuts, folds again (so a cut cannot strand a sign before the code text that follows) and quotes: used by `shown()` in `render.ts` for every agent-authored text and by the router for stranger text in `message_taken` flags. Property tests check every non-letter, non-number code point of planes 0–3 and 14–16 as a gap, every `\p{Nd}` digit, every code point whose NFKC form or confusable prototype is a tail letter, every '#' look-alike before every digit-like letter, every `\p{Lm}` between `#` and a number, every non-plain letter of all planes after `#`, and every plain letter in a one-letter or number-ended word after `#`.
- Reserved line heads (M7, `lineHeads.ts`, best effort): after the neutralizer, a reply line whose head word reads `today` or `system` is folded to `Today -` / `System -` (head kept as written) unless the next character that is not a space or ignorable is a letter or digit after a space (a new word: `Today is Friday`; modifier letters such as `ː` do not count), the end of the line, or one of `, . ! ? / ' ’ -` (sentence punctuation, `/` between alternatives and the possessive: `Today, you have…`, `Today/tomorrow works`, `Today's plan`; `-` is the fold's own mark, so the fold is idempotent). There is no list of colons: anything else right after the head (`:`, a visarga `ః`, `፥`, `;`, a letter of another script with no space) folds, and that character and the spaces before it become ` -`, with a space added when a word follows directly (`Today:Waiting` → `Today - Waiting`); an emoji, an opening bracket or quote (the ASCII `"` included: `Today "big" day` → `Today - "big" day`), or a currency sign is kept after it (Ps, Pi, Sc by category: `Today (Friday) is busy` → `Today - (Friday) is busy`, `Today 🎉` → `Today - 🎉`). The allowed punctuation must itself end the head (a space, a line end, a letter or digit, or an emoji after the run): `Today.: Waiting` and `Today,꞉ x` fold to `Today - …`. Ordinary text it still changes: `Today & tomorrow` → `Today - tomorrow`, `Today; tomorrow` → `Today - tomorrow`, `Today #1 priority` → `Today - 1 priority` (meaning can be lost; it is a best-effort layer). The head word runs while each character reads as a Latin letter or digit on a confusable skeleton like the `untrusted` tag: any case, leading spaces, default-ignorables and non-spacing marks skipped, diacritics stripped, every look-alike Unicode confusables.txt lists for t/o/d/a/y/s/e/m folded (generated table `lineHeadLookalikes.ts`, plus hand-picked extras), each character looked up as written, upper-cased and lower-cased (so `Տ` U+054F and `ⲙ` U+2C99 are caught), o-like digits (`0`, `०`) read as o, Latin `rn`/`cl` read as m/d; every line break a reader sees (`\n`, `\r`, U+2028/2029/0085, `\v`, `\f`) starts a line. This makes it harder for a model fooled by an email or invite to show the owner a digest header or a transcript system line; it is not a guarantee.
- `wrapUntrusted(source, text)` (`email|calendar|stranger|notes|agent`): NFKC + invisible (Cf) characters removed, any `<` (or bracket look-alike) that starts a tag named `untrusted` inside the content becomes `‹`; the name is matched on a confusable skeleton (default-ignorable and combining marks skipped, case and diacritics folded, Cyrillic/Greek/Armenian/small-capital look-alikes such as `е` U+0435 or `ѕ` U+0455 folded to Latin), with a bounded look-ahead so the pass stays linear. `search_history` taints (Violet's side of the owner thread can quote third parties) and wraps each of Violet's messages as `agent`. Tools with `taints: true` set `ctx.turn.tainted` when they succeed.
- **Prompt-last (I19).** The Brain runs its tool loop inside `runInTurn(messageId)` (`approvals/turn.ts`, AsyncLocalStorage). An approval requested there (calendar tool, `a2a_release` from `release.ts`: the decision is in the service, no caller changes) is created **held** (`hold_until` = now + `TURN_HOLD_MS` 15 min = the turn deadline `BRAIN_TURN_MS` 8 min plus a 7 min margin for the last tools and the reply, so strictly longer than one attempt of the turn can run (S2); each attempt of the turn renews the hold of the prompts an earlier attempt left (`holdTurn`), so a job retry never lets it lapse mid-turn; `turn_message_id` = the message) and not delivered — on the existing-key and raced-insert paths too. After the reply is sent (or none, or the fixed model-error text) and before `memo.finish`, the turn runs `Brain.beforePrompts` (M4 sends this agent's pending a2a notices, e.g. the `Talking to …` line) and then `approvals.deliverTurn(agentId, messageId)`: that turn's unsent prompts in creation order, hold ignored (also orphans of an earlier attempt of the same turn; `claimSend` keeps a retry from sending twice), then the hold is cleared. The first step of closing writes a closing mark for the turn (a reserved `brain_tool_memo` row); an attempt that finds it — a retry after a crash between the prompts and `memo.finish`, or a stale-requeued duplicate run still in its model loop — sends no model text and only closes, so a retried or duplicate run normally sends no reply after the turn's prompts. The check and the mark are not atomic: two runs of one turn that both pass the check before either marks it (only a stale requeue makes two runs at once) can put one reply below the prompt. That fails closed: a bare yes under that late reply is conversation for the Brain and approves nothing (I19), and the prompt's button and a reply-to on it still answer it. The sweep and `sendUnsent` skip held rows until `hold_until` (the crash net: a turn that died gets its prompt out late). Approvals requested outside a turn (a2a outcome jobs, anything on its own job) are delivered at once. `request_calendar_event` refuses with fixed tool errors a start in the past or more than 366 days ahead, a prompt that would not show the whole title and location, and a time that overlaps an event of a pending approval of a `jointBooking` kind (`a2a_outcome`: answer that prompt instead, P13), or of one this owner already approved while its plan still waits for the other owner (`jointOpen`: the conversation is still `awaiting_approval` or booking); times are whole minutes; there is no description. Otherwise it returns a fixed text: `The owner gets a yes/no prompt for this right after your reply. Do not repeat it or ask them to confirm in your own words. Nothing is booked unless they say yes.` (paused: it will ask when it can send again). Brain replies (and its fixed texts) are stored with `meta.from = 'brain'`.
- Idempotent per `messageId`: `brain_turns` marks a finished turn (never re-run, never a second reply). `sideEffect` tools are memoized in `brain_tool_memo` by (message, tool, canonical-JSON input hash, occurrence) and get `ctx.callKey` as idempotency key (approvals use it as `idempotencyKey`; notes derive their id from it). Draft creation has no provider key: a crash between `createDraft` and the memo write can repeat it.
- Failures: a retryable `LlmError` (or any non-LlmError) fails the job, which retries the turn (`job.retry`). Non-retryable → one fixed apology; `unconfigured` → a fixed "model not connected" text. Refusal → a fixed text. Every other early stop ends with a fixed notice, so the owner is always told the turn stopped: `max_steps`, `max_tokens`, `model_context_window_exceeded`, `deadline` each have their own, any other stop reason a generic one; model text that came with tool calls that never ran is dropped (it may promise what did not happen), other model text is kept above the notice. Only `end_turn` (or `stop_sequence`) with an empty final text sends nothing; a text that is empty once made storable (only NULs or spaces) counts as empty, and the gateway never sends an empty text (`outbound.suppressed` reason `empty`).
- Turn deadline (`BRAIN_TURN_MS` 8 min, below the job stale time of 10 min): measured on the `Clock` from the start of the model loop; no model call starts after it, and the call in flight gets the time left as `timeoutMs` (the SDK's own timeout of 5 min and its retries are cut off there), so a running turn is not requeued as lost while it talks to the model. Reached → stop reason `deadline` and its fixed text; not retried.
- Times in tool inputs: ISO 8601 with explicit offset only; outputs in the owner's zone (`Fri Nov 13, 7:00–8:30 PM [2026-11-13T19:00:00-05:00 → …]`). Range tools take ≤ 31 days.
- Brain tools get read-only calendar access, no gateway and no transport: no tool sends email, writes the calendar, approves, pauses or messages anyone but the owner (approval prompts are sent by the approval service).
- Action names (I15): `brain.turn` (outcome, stopReason, steps, tools, tainted, usage, models, fallback: the models that served the turn as the API reported them, and whether the refusal fallback answered), `tool.call` (tool, ok, memoized), `tool.denied` (tool, reason), `gmail.draft_created`, `note.saved`.

Brain tools (M2): `get_schedule`, `find_free_time`, `request_calendar_event`, `search_email`, `read_email`, `draft_email`, `remember`, `recall`, `search_history`, `list_messages_taken`, `list_pending_approvals`.
Added by M4: `talk_to_agent`, `tell_envoy`, `list_agent_conversations`, `read_agent_conversation`, `send_transcript_to_owner`, `end_agent_conversation`.

### 8.3 Approvals

- `approvals.request(agentId, { kind, payload, groupId?, expiresAt? })` → the registered kind renders a **one-line** prompt from the payload → sent at once (inside a Brain turn: right after the turn's reply, 8.2): `#7 Dinner — Fri Nov 13, 7:00–8:30 PM. Book it? Reply yes or no.` (with yes/no buttons where the transport supports them). Every message the service sends as the prompt of one approval is a **genuine delivery** (`approval_deliveries`): the first delivery, a re-prompt, a "Which one?" copy.
- **Resolver (I19): a typed yes or no counts only directly under the real prompt.** Grammar (unchanged): `yes|y|yep|yeah|ok|okay|sure|approve|do it|go ahead|👍` / `no|n|nope|nah|don't|decline|cancel|👎`, optionally followed by `#?<ref>`. Buttons `approve:<id>` / `deny:<id>` resolve at once, as before; paused: the resolver does not run. For a typed decision m, **RUN(m)** = the unbroken run of genuine deliveries directly above m in the chat's own numbering (`chatOrder.ts`): start at the message numbered n(m) − 1 and walk up while each is a recorded delivery of this agent (at most 20); stop at the first that is not, or is unknown. Then:
  - (a) **Reply-to** (checked first). It names a genuine delivery of a pending approval A, and m has no ref or A's ref → resolve A. A delivery of an approval no longer pending → `#n isn't open any more.` Anything else (a message that is not a delivery, e.g. a model reply that looks like a prompt, or a ref that conflicts with the prompt replied to) → resolve nothing; go to (d)/(e), with the ref's approval as the target if there is one.
  - (b) **Explicit ref**, no reply-to. A must have existed before m (else, or not pending: the not-open line). A delivery of A in RUN(m) → resolve. Otherwise (d) re-prompt A.
  - (c) **Bare answer**, no reply-to. RUN(m) names exactly one approval and it is pending → resolve it; it is closed → `#n isn't open any more.` RUN(m) names two or more distinct approvals → (e) with those still pending in RUN(m), and only those (one left → (d); none → `That one isn't open any more.`), even if the others closed between m's arrival and the resolver running: what the owner saw above m counts, so a closing in that window never turns an ambiguous yes into a yes for the other one. None: Q = the approvals answerable today (existed before m and prompt delivered before m, `listAnswerable`). Q empty → not handled (the Brain gets it). Otherwise, if the message directly above m is a Brain reply (`meta.from = 'brain'`) or an Envoy question (purpose `question`) — it may itself ask the owner something — or the word is a weak acknowledgement (`WEAK_ACKS`: `ok`, `okay`, `sure`, `👍`): not handled, the Brain gets it (it cannot approve). Else one in Q → (d); several → (e). (A bare answer after a non-prompt reply-to follows the same Q rule, with the weak-ack exception but not the conversation one.)
  - (d) **Re-prompt**: claim first (insert the `approval_deliveries` row `(for_message_id = m, approval_id)`; only the inserter sends), then send the stored prompt again as one new message through the same gateway call as the first delivery (purpose `approval`, buttons, tainted per kind) with the fixed prefix `Just to be sure: `, then record its transport id; `approval.reprompted {approvalId, ref, messageId, reason}` (`sent: false` when suppressed or failed; the claim stays, so it is never sent twice). Only for a pending, unexpired approval. Nothing is resolved; the Brain does not run.
  - (e) **Which one**: claim every row first (all or none, one transaction), then the fixed line `Which one? Tap Yes or No under it, or reply yes and its number.` (no quoted text, no refs; `N more are waiting after these.` when more than 5), then each answerable pending prompt re-sent as its own genuine delivery (kind `which_one`), oldest first, at most `WHICH_ONE_LIMIT` = 5; `approval.ambiguous`. After it, `yes 2` finds #2 in RUN and resolves; a bare yes gets (e) again (each one needs a new owner message, so nothing loops).
  - A claim for (d)/(e) that is lost because a candidate closed meanwhile is never silence: the choice runs once more with fresh candidates; lost again → `That one isn't open any more.` (A claim held by another run of m: that run answers, (g).)
  - **Next in the run (S1).** After a typed answer resolves an approval (rules a–c), if exactly one other approval delivered in RUN(m) is still pending, the resolver shows its prompt again right below the confirmation line: a genuine re-prompt delivery (claimed per `(m, approval)` first, so a retried hook sends it once; `approval.reprompted` reason `next_in_run`; not while paused). The next bare yes or no is then directly under it and answers it by the rules above. Two or more others pending: nothing is shown again. A button press takes no chat number, so its RUN is empty: nothing is shown again after a button.
  - (f) yes and no follow the same table (a no has effects too). (g) Retries: everything is pinned to m's own number and to rows keyed by m: a hook that runs again (a stale requeue, a retried job) finds `resolved_by_message_id = m` and finishes that resolution, or finds a claim for m and sends nothing more; its own re-sends sit below m, so they are never above it.
- **Transport numbering.** Telegram: inbound `chatMessageId` = `<chat id>:<message_id>`, outbound ids the same shape (8.1, Telegram transport; not verified live: if the numbering is off, typed answers fail closed and the buttons still work). A transport without numbering (no `chatMessageId`): every typed answer re-prompts; reply-to and buttons work. A gap (a message the app never saw, a stranger if numbering were shared across chats), an unknown or malformed id, another chat (pairing reset) → not above. Owners never cross: deliveries are looked up per agent.
- Arrival checks (`existedBefore`, `listAnswerable`) fail closed when the message's arrival is unknown (`COALESCE(…, false)`).
- Kinds register `{ schema, render(payload, { timezone, now }), onApproved?, onDenied?, onExpired?, calendarEvents?(payload), booked?(payload, { timezone, now }), guard?(approval), latestExpiry?, quotesThirdParty?, jointBooking? }` (`src/approvals/types.ts`). Time text in prompts, Booked and failure lines is `exactRange` (`brain/time.ts`): the `formatRange` text, plus the year whenever the start or end is not in the owner's local year of `now`, and the UTC offset for a local time that occurs twice; with starts limited to 366 days ahead and whole minutes, the text determines the (start, end) pair. `calendar_event` payload: `title`, `start`, `end`, `location?` (no description; an older stored payload with one is booked without it), text stored canonical (`approvals/eventText.ts`: one line, folded as `quoteFolded`, NFKC, double quotes made single, number signs dropped), shown whole: `Dinner — Fri Nov 13, 7:00–8:30 PM at “Luigi's”. Book it?`. M2: `calendar_event`. M4: `a2a_outcome`, `a2a_release` (both `quotesThirdParty`: their prompt messages are stored tainted; `ApprovalService.quotesThirdParty(kind)`).
- `request(agentId, { kind, payload, groupId?, expiresAt?, idempotencyKey? })` validates with the kind's schema, stores the parsed payload, allocates the ref, and composes the prompt **by code**: `#<ref> <render(...)> Reply yes or no.` — the rendered part is sanitized (control characters and line breaks stripped), NFKC-normalized, every number sign (`#`, `＃`, `﹟`) removed, at most 240 chars; a rendered part longer than that is refused (`PromptTooLong`), never cut. A kind may cap the expiry with `latestExpiry(payload)` (`calendar_event`: the event's start). Buttons: `approve:<id>` / `deny:<id>`. Paused → stored unsent; `onResume` and the sweep send unsent pending prompts (after expiring what lapsed, so a stale prompt is never sent). Every send first takes an atomic claim (`prompt_sending_until`, 2 min lease), so concurrent senders deliver a prompt once. A delivered prompt is never sent again (I15): if recording its transport id fails twice, the lease is held to the expiry and the id kept in the process, and the next pass over it (resume, sweep) only records it; after a restart in between, that prompt has no delivery row, so its button still answers it but a typed yes under it does not. The same `idempotencyKey` returns the existing approval.
- Resolution: one `UPDATE … WHERE status = 'pending' AND expires_at > now` setting `resolved_by_message_id`; a retried hook finds its own resolution by that id and re-runs the (idempotent) callbacks. `approval.approved` / `approval.denied` carry `via` (`text`|`button`) and, for text, `basis` (`reply_to`|`run`). `onApproved` / `onDenied` return the one-line reply (defaults: `Okay, approved #n.` / `Okay, not doing #n.`). Not open → `#n isn't open any more.` A button for an approval of another agent resolves nothing. Before targeting, the resolver expires pending approvals past `expires_at` (the sweep does not run while paused), so a late yes gets the not-open text (by ref, reply-to or button; a bare one directly under the expired prompt gets the not-open line too (rule c), and a bare one under anything else with nothing else open goes to the Brain, which cannot approve); `listPending` likewise omits them, and `executeApproved` refuses an approval resolved after its expiry.
- `cancel(id, reason)`, `get`, `listPending`, `expireDue`, `sendUnsent`; `approvals.calendar` is the `CalendarWriter`: `executeApproved(id)` (requires `approved`, runs `guard`, books `calendarEvents(stored payload)` with keys `approval:<id>:<n>`, records `calendar_writes` (M4, I7: the row — `event_id` NULL — is written BEFORE `createEvent` and the id filled in after, so an event the provider made but whose response was lost, or a crash in between, is still found by its idempotency key via `eventIdForKey` and undone; an error in that undo is logged and the row stays live for the caller's retry), marks `executed`; an event that has already started is refused (`failed`, "the event has already started"); right before each write it reads the owner's agent row `FOR SHARE` and, if paused, writes nothing more: with nothing of the approval's group written yet it returns `{ ok: false, held: true }` and leaves the approval `approved` (logged `calendar.write_refused` reason `paused`; 8.6), otherwise it fails as below; a failure undoes what it wrote and marks `failed` with a safe reason; anything not `approved` throws `CalendarWriteRefused`) and `undo(id)`.
- Booked items: a kind with `booked(payload, { timezone, now })` gets one `digest` flag of kind `booked` from `CalendarWriter` once its events are booked (`codeLine` in `line.ts`, which `composePrompt` uses too: one line, NFKC, number signs removed, ≤ 240 chars; dedupe `booked:<approval id>`). It is raised again (a no-op) every time `executeApproved` finds the approval `executed`, so a crash between booking and flag is repaired by the retried resolution. `calendar_event`: `Dinner — Fri Nov 13, 7:00–8:30 PM`. A denied or failed approval raises none.
- Default expiry 24 h. The per-agent `approvals.sweep` (every minute) marks expired, calls `onExpired`, raises a `digest` flag, and sends unsent prompts (not those a Brain turn still holds).
- Action names (I15): `approval.requested`, `approval.approved`, `approval.denied`, `approval.ambiguous`, `approval.reprompted`, `approval.not_open`, `approval.cancelled`, `approval.expired`, `approval.executed`, `approval.failed`, `calendar.event_created`, `calendar.event_deleted`, `calendar.write_refused`.

### 8.4 Agent-to-agent (open conversation)

Start: owner tells the Brain what they want → Brain calls `talk_to_agent({ with, topic, brief, window_start?, window_end? })` → taint rule + `EgressGuard` (I11) → conversation created, `open` message (topic + brief + window) delivered to the peer over the internal channel (a job on the peer's lane) → owner sees code-rendered: `Talking to Sam's Violet about "Dinner Friday": "<brief>"`.

Each delivery runs one **Envoy turn** on the receiving side: context = own brief + own owner's guidance + transcript (peer text wrapped as untrusted) → tool loop with the seven Envoy tools → exactly one outward act (`say`, `propose`, `accept`, `decline`, `ask_owner`, `end_conversation`).

- `propose({ summary, events: [{ title, start, end, location?, calendars: 'both'|'mine'|'theirs' }] })` — 0 to 5 events. Zero events = an agreement with nothing to book.
- `accept({ proposal_seq })` — code validates the proposal, re-checks free/busy for every calendar it touches, then creates one `a2a_outcome` approval per owner, rendered by code from the stored proposal. Both yes → `CalendarWriter` books on each calendar (separate events, no invites sent), both owners get "Booked: …". One no → the other owner's prompt is cancelled and they are told "Sam said no to: …"; the conversation waits for new guidance from the owner who said no.
- `ask_owner({ question })` → owner gets one line at once; the Brain relays the answer with `tell_envoy` (same I11 checks; the question taints the turn, so the answer is held for the owner's yes on the exact words, I20) and the Envoy resumes.
- Limits per I12. Idle 24 h → expired (never a conversation whose booking is being made, or held for a pause: 8.6). Every message is stored; either owner can ask for the full verbatim transcript (`send_transcript_to_owner` sends code-rendered text, not a model paraphrase). The owner can also type `transcript` (trimmed, any case): an owner interceptor after the approval resolver, before the Brain, sends the transcript of their latest conversation (the one started last; purpose `transcript`), or `No agent conversations yet, so there is no transcript.`, with no model call; held while paused like every owner message; logged `a2a.transcript`.

**Settled details (M4)**

- *Lock order (m4fix).* Agent row before conversation row, never the reverse: `app.ingest` / the router's `route` step / the flag policy / the digest build lock the agent row (`FOR UPDATE`) and never touch a conversation row in that transaction; an Envoy act, owner guidance, an owner's end and an open (household row) take their own agent row `FOR SHARE` first, then the conversation (or household) row (I14: refused while paused); every other conversation-locking transaction (outcome reopen/settle, idle expiry) locks no agent row (its inserts take only FK `KEY SHARE` locks, which never wait on a lock that waits on a conversation). The booking claim reads both agent rows `FOR SHARE` (in id order; refused while either is paused, I14), then is one `UPDATE` of the conversation row reading the group's approvals (no approval row lock; only a claim that fails a part-done booking closed during a pause, 8.6, then marks the group's `approved` rows failed, after the conversation row, as the held-expiry settle does). A real-Postgres stress test (two apps, both owners texting and approving at once, 20 runs) covers it.
- *Internal channel.* A message is a row written by `writeMessage` inside a transaction that holds the conversation row lock: `seq` = `last_seq + 1`, the row, one `a2a.turn` job per receiving agent (lane = that agent, dedupe key `a2a:turn:<conv>:<agent>:<seq>`) and its `a2a.message` log row commit together. No Transport is involved. Deliveries: `open`/`text`/`proposal`/`decline` → the other side; owner `guidance` → own side; "slot gone" `system` → both; `accept`, `close`, `question`, other `system` rows → none.
- *Envoy turn* (`envoy.ts`, mind `envoy`, ≤ 6 steps): idempotent per turn key `<conv>:<agent>:<seq>` (`a2a_turns`, like `brain_turns`). Its outward act is the message carrying the turn key (unique), so a retry finds it and never calls the model or acts again. Paused agent → the turn is `waiting`; an act during a pause is refused (the act transaction reads the agent row `FOR SHARE`, ordering it against the pause flip). No outward act → nothing sent, side `stalled`, one `a2a_stalled` digest flag per conversation and side. A non-retryable model error counts as no act. The turn has a wall-clock bound (`ENVOY_TURN_MS` 5 min, E1, as the Brain's): no model call starts after it and a call in flight is cut off at it (`timeoutMs`), so the tools of a cut-off call never run; a turn so cut with no act is a no-act turn (stalled, its owner told).
- *Envoy context* (`envoyPrompt.ts`): system = rules + both first names; dynamic = time, zone, topic (wrapped when the peer chose it), this side's window, remaining budgets, live proposal; one user message = own brief (or the default posture) + every visible message. A proposal's `calendars` is shown for the reader, from the stored agent ids (`mine` = the reader's owner only, `theirs` = the other owner only). Brief, guidance and system rows are plain instructions/data; every Envoy-written text (peer's and own) is wrapped `<untrusted source="agent">`. Code reads only a2a tables, agent/owner names and zone, and `freeBusy`.
- *Windows (I10).* Set only by the initiator's owner (≤ 31 days, must end in the future). The initiator reads all of it, the responder its first 7 days; reads are clipped to that and to now; none → refused. Proposed events must lie inside the whole window (when there is one), start in the future and at most 366 days ahead, whole minutes, last 5 min – 24 h; ≤ 5 events, title ≤ 120, location ≤ 200, summary ≤ 500 chars; `calendars` is resolved to agent ids when stored.
- *Accept* re-validates the proposal (events, and that both owners' prompts can show it whole) and re-checks free/busy (results never reach a model as data). Because a "slot gone" result reaches both Envoys, the accept-time check is held to what availability may reveal (I10): for each side, only the proposal's events on that side's calendar that lie inside that side's effective window are checked, and only while that side has availability budget left (it costs that side one call). Anything not checked at accept — no window, outside the responder's 7 days, no budget — is still checked by the booking guard right before writing, after both owners said yes. Busy → a `system` "That time is no longer free, so nothing was booked." to both Envoys. Free → `accept` row, status `awaiting_approval`, a new `outcome_group_id`, and an `a2a.outcome` job per owner that creates that owner's `a2a_outcome` approval (idempotency key `a2a-outcome:<group>`; cancelled at once if the conversation moved on meanwhile).
- *Booking.* `onApproved`: sibling pending → `Waiting for <name>.`; else one atomic `UPDATE` claims the booking (`outcome_state = 'booking'`, a 2-min lease, `outcome_claimed_by` = this approval's id) only while both approvals of the group are approved/executed/failed — so whichever yes comes second books, exactly once. A retry of the same hook takes its own claim over at once; anyone else only after the lease ran out (a concurrent yes that loses the claim hears `Booking it now. I'll tell you when it's done.` and gets the result as a notice). Booking is **resumable** (I7): it runs `executeApproved` for its own approval then the sibling's (the guard re-checks sibling, accepted proposal, booking state and a fresh free/busy unless that approval already has writes); every step is idempotent and derived from the approvals' own state and `calendar_writes`, so a retry continues where the last attempt stopped. If either side failed, both approvals' writes are undone; an undo error is caught, and if any event is still on a calendar the group stays `booking` (lease released), both owners are told `Couldn't book …: a calendar didn't accept it. It is still on <your / Sam's> calendar for now; I'm removing it …`, and the sweep retries. The `a2a.sweep` first resumes every `booking` group whose lease ran out (a worker that died between the two writes, a hook out of attempts, a failed undo) and tells both owners the result by notice; the idle sweep never closes a conversation that is `booking`. An owner may end a conversation while it is `booking` (`end_agent_conversation`): it is closed at once (the tool says the booking is still being settled) but keeps `outcome_state = 'booking'`; the booking guard then refuses every further write ("the conversation was ended"), and the sweep — which resumes every `booking` group whatever the conversation status — undoes whatever is on a calendar, records `outcome_state = 'failed'` (or `booked` if both writes had already landed) without reopening, and tells both owners. Success → conversation closed `booked`, the other owner gets `Booked: …` (notice), `a2a.booked`, flags `a2a_booked` + `a2a_closed`. Failure (once nothing is left on either calendar) → reopened with a system message (slot gone: delivered to both Envoys), both owners get `Couldn't book …: <reason>. Nothing was booked.` (`failureWhy`: only reasons true for both owners are named — `that time is no longer free`, or `Google isn't connected on this server` in production without Google, where an outcome both approve is never booked and nothing retries; otherwise `a calendar didn't accept it`), `a2a.booking_failed` (`undoPending` while an undo is outstanding). `no` → conversation reopened, the no-sayer's side `awaiting_owner`, the sibling cancelled, its owner told `<name> said no to: …`; expiry → `No answer from <name>, so nothing was booked: …`.
- *Releases (I11, `release.ts`).* Topic/brief/guidance are canonicalized first (one line, NFKC, inner double quotes → `'`, number signs dropped) so the prompt shows the stored text exactly. EgressGuard runs on every release; then the release is held as `a2a_release` (`#8 Tell Sam's Violet[ about “topic”[ (Fri Nov 13, 6:00 PM – Sat Nov 14, 12:00 AM)]]: “…” Send? Reply yes or no.`; the window is code-rendered by `releaseWindowText` in the owner's zone — the `formatRange` text, plus the year whenever the start or end is not in the year of the request (`requestedAt`, stored in the payload, never sent) and the UTC offset for a local time that occurs twice (the DST fall-back hour) — so the shown text determines the stored window exactly; `talk_to_agent` rounds it outward to the minute — start down, end up — before it is stored or checked, in tainted and untainted turns alike, so nothing crosses at a precision the owner was not shown: seconds, the year or the repeated hour could otherwise carry hidden data; must fit the 240-char prompt, else a tool error asks to shorten) whenever the turn is tainted (I20: for every release action, opening and guidance alike, whoever's words they are — there is no owner-verbatim exception), or when the calendar could not be read. The release is requested inside the Brain turn, so its prompt is held like any other (8.2 prompt-last): reply, the turn's notices, then the prompts in creation order. The held tool result is a fixed text (`heldText`): `Not sent. Nothing has gone to <peer>: <owner> gets a yes/no prompt showing the exact text after your reply, or when I can send again, and it goes out only if they say yes. Tell <owner> you will check with them first; do not say it was sent, and do not repeat the prompt or ask them to confirm in your own words.` (one text, true whether or not a pause lands after the call); no ref, so the model has no `#n` to copy. The approval's idempotency key is the tool call's `callKey`, so a retried Brain turn finds the same approval; `release` looks that approval up first, tainted turn or not: a pending one stays held (inside the turn `request` returns it undelivered; `deliverTurn` sends it once after the reply, one `prompt` delivery row, never inside the tool call), an answered one is reported (yes: already handled, not sent again; no/expiry: a tool error), so a retry never releases what the owner refused and never releases twice. Yes → released exactly as stored (key `approval:<id>`, so a retried hook never releases twice) and the approval marked `executed` (a refusal: `failed`, never retried); no/expiry → dropped, nothing retries. A yes whose release runs after a pause landed (I14) does not cross: the approval stays `approved`, the refusal is logged (`a2a.tool_denied`, reason `paused`, with the approval id), and the a2a `onResume` hook carries out only approvals so logged, once, with the usual notice (or one `Couldn't send #n: …` line); a row left `approved` for any other reason is never sent by it. Released → `Talking to Sam's Violet about “…”: “…”` / `Told Sam's Violet: “…”` (released at once in a turn: a notice, sent before the turn's prompts; released by a yes: the reply to that yes — a held release shows no `Talking to …` line before it). Untainted turns are released at once (EgressGuard still applies): e.g. a first request from a clean history.
  *What I20 costs the owner:* one more tap per instruction to another agent once the Brain has seen third-party text, and it does not wear off by itself. Turns are tainted while third-party text is in the Brain's history or context (an open conversation the peer started, an Envoy question, an outcome prompt or agent notice in the last 40 messages, or a tainting tool earlier in the turn; a tainted text that was delivered but whose `messages` row could not be stored — `outbound.sent` `recorded: false`, `tainted: true` — taints every later turn, so a storage failure never makes a turn start clean), and every reply the Brain writes in a tainted turn is stored as tainted (`meta.tainted`, it may repeat what it read), so the newest such reply is always inside the 40-message window while the owner keeps talking to Violet: from then on every instruction to an agent — including the answer to an Envoy question — shows the exact words and waits for yes. Letting the taint decay would be a change to the history rule, not made here. A conversation the owner opened, whose peer replies only in the conversation (text the Brain has not read), does not taint by itself: the next `tell_envoy` goes out at once, because the Brain has seen nothing a third party wrote. The Envoys' own negotiation (proposals, free/busy, accept) needs no extra taps. Typed owner messages under I19 and I20 (`test/unit/seam/cost.test.ts`): the first dinner in a clean chat 3 (Alex's request, Alex's yes, Sam's yes); a second request once the chat is tainted 4 (request, yes to the words, yes to the booking, Sam's yes); two releases held by one turn, typed answers only, the request + 2 (`yes 1`, after whose confirmation Violet shows #2 again (S1, 8.3), and the `yes` under it sends it; reply-to or the buttons answer each in one); the demo 7 (Alex: dinner, yes, pause, resume; Sam: yes, the run request, yes to its words).
- *Tokenization (`words.ts`).* NFKD, combining marks dropped, lowercase; tokens = maximal runs of `\p{L}\p{N}`. Stop words (glue: articles, prepositions, pronouns, auxiliaries, contraction pieces `s t d ll re ve m`, please/yes/no/ok/tell/ask/say, wh-words) are never significant; both owners' first names and the agents' names are never significant in the EgressGuard. (The owner-verbatim exception that used these tokens was removed by I20: no word match can tell what the owner meant to keep private.)
- *EgressGuard phrase match.* Private fields = title, location, description and each attendee of the owner's events in the next 31 days and in the conversation window. Blocked if, for some field, (1) a token with ≥ 3 characters that is not a stop word, not a common word (weekdays, months, times of day, meals, generic event/scheduling words, small number words, all-digit tokens) appears in the release and not in the owner's message; or (2) two consecutive significant tokens of the field, not both common, appear consecutively (stop words skipped) in the release and not in the owner's message ("Dr Ng"). Blocked → tool error ("rewrite without that detail"), `a2a.release_blocked` (match count only).
- *Questions (D4).* `ask_owner` stores a private `question` row and a notice `Violet ↔ Sam's Violet (“topic”) asks: “…”` (purpose `question`). While the side is `awaiting_owner`, unanswered questions appear in the Brain's dynamic context inside an untrusted block (tainting the turn); `tell_envoy` guidance clears it and runs the Envoy. The Brain's dynamic context also lists open conversations (id, peer, topic, status); a topic the peer chose is wrapped and taints the turn.
- *Owner-facing text (`render.ts`, I13).* Agent text goes through `shown()` = `quoteFolded` (8.2): folded, sanitized, cut, folded again, and quoted with curly quotes it cannot close. Outcome prompt: `With Sam: “Dinner” — Fri Nov 13, 7:00–8:30 PM at “Luigi's”. Book it?` (several: `; `-separated, `Book them?`; none: `With Sam: agreed “<the whole summary>”. OK?` — never cut). An event that does not go on this owner's calendar says so: `… (only on Sam's calendar)`, also in the Booked and failure lines (P7). What you see is what gets booked (P2): every title and location is shown whole (`propose` stores them canonical, as `calendar_event` does), times by `exactRange`; there is no shorter form. A proposal whose prompt does not fit the 240-char body for BOTH owners is refused at `propose` and `accept` (`prompt_too_long`: fewer events, or shorter titles or locations), and the outcome job fails closed (conversation reopened with a system message to both Envoys, nobody asked, `a2a.limit` `prompt_too_long`). Transcript: header plus one line per visible row (`Sam's Violet: “…”`, `Violet proposed (proposal 3): “Dinner” — … at “…”, on both calendars. Summary: “…”`, `Alex told Violet: “…”`, `System: “…”`). It is complete: every stored text is shown whole (caps are the stored limits, `PROPOSE_MAX` in `envoyTools.ts` for proposals, with room for folding), the open line shows the window (`releaseWindowText`, or `no time window`), accept and decline lines name the proposal, and each event says whose calendars it is on for the owner reading (`on your calendar only`, `on Sam's calendar only`).
- *Flags (I17).* `a2a_opened` (to the responder), `a2a_closed` (both), `a2a_booked` (both), `a2a_stalled` — all `digest`, raised by the `a2a.after` job / the Envoy turn. Digest sections: `a2a_opened`, `a2a_closed`, `a2a_stalled` → `Agent conversations`; `a2a_booked` → `Booked` (one line per booking: `a2a_outcome` has no `booked()`, so no generic `booked` flag). Notices (questions, `Talking to …`, `Waiting for …`, `Booked: …`, `… said no to: …`, booking failures) and outcome prompts are not flags: sent at once, also in quiet hours, outside the daily budget, held only while paused (I14) or while no owner chat is paired.
- *Limit refusals* are logged as `a2a.limit` with `limit` = `not_household`, `open_per_pair`, `new_per_day` (rolling 24 h, closed ones count), `messages_per_side` (the 13th outward act closes the conversation `limit`), `questions_per_side`, `availability_budget`, `no_window`, `outside_window`. Other refusals (`second_act`, `own_proposal`, `stale_proposal`, `invalid_event`, `prompt_too_long`, `not_open`, `paused` — outward acts, `check_availability` and the Brain's `talk_to_agent` / `tell_envoy` / `end_agent_conversation` alike, unknown tool, invalid input) as `a2a.tool_denied`. Idle sweep: global scheduler task `a2a.sweep` (every 10 min) resumes lapsed bookings, re-queues `waiting` notices of agents that are not paused and have an owner chat (a re-pair after `--reset`), and closes conversations idle ≥ 24 h (`expired`), cancelling pending outcome approvals. An owner can end one with `end_agent_conversation` (same cancellation).
- Action names (I15): `a2a.opened`, `a2a.message` (every message, both directions), `a2a.envoy_turn` (outcome, act, stopReason, tools, usage, models, fallback), `a2a.tool_denied`, `a2a.availability` (window asked, interval count), `a2a.release` (text hash + length, conversation or approval id), `a2a.release_held` (reason `tainted` | `calendar_unreadable`), `a2a.release_blocked`, `a2a.limit`, `a2a.outcome_requested`, `a2a.booked`, `a2a.booking_failed`, `a2a.closed`, `a2a.transcript`.

### 8.5 Flags, digest, proactive

- `now` flags: one line, at once, within budget and quiet hours (I17). Approval prompts and Envoy questions are never budgeted (they do not go through flags). A paused agent texts no flag: it becomes a digest item.
- `digest` flags: held. At the owner's local `digest_hour` (default 18:00), once per local date, code renders the digest: messages taken, agent conversations opened/closed, drafts created, things booked, approvals still waiting, overflowed flags. Empty → nothing sent.
- Conflict check: hourly, looks 36 h ahead for overlapping events; a new overlap raises a `now` flag once (dedupe key = the event pair).

**Details (M5, `src/flags/`).** All rendering is code; no model call.
- *Now policy* (`policy.ts`, installed by `flagsModule` through `app.flags.setNowDelivery`, so captured `FlagService`s keep working). Each delivery decision runs in one transaction under the agent row lock (`FOR UPDATE`): paused → digest item (`flag.overflow` reason `paused`); quiet hours [22:00, 07:00) owner-local → `held_until` = next 07:00 (`flag.held`); else, if held flags of the agent are already due (`held_until` ≤ now), they are texted first, oldest first, before this flag decides (so a flag raised before the 07:00 release tick never takes the budget ahead of them); then the owner-local date's budget (3; a reserved send counts) → reserve and send, or digest item (`flag.overflow` reason `budget`, `held: true` for a released one). A send holds a 2-minute lease (`attempt_at`); a retryable failure frees it, sets `retry_at` (backoff 1 min doubling to 15 min, at least the transport's `retryAfterMs`) and rethrows (a retried raise finishes the delivery at once; only the release task waits for `retry_at`), a permanent one or a suppressed send makes the flag a digest item (`send_failed` / `suppressed`, budget refunded). A lease left by a crash is retried after it expires unless the gateway already recorded that text. Scheduler task `flags.release` (every tick) texts due held flags oldest first (`flag.released`) and retries failed sends; it looks again until no new flag is due, so a flag that waited during the run is decided in it. Order is strict across releasers (two apps, or a raise racing the tick): a released held flag is not claimed while an older `now` flag of the agent is still due or in its send lease; the releaser that holds the older one texts it next. A released flag whose send fails (retryable) gets its `held_until` back, so it stays due and the younger ones still wait for it.
- *Digest* (`digest.ts`). Task `digest.run` (every tick) per agent: due from `digest_hour` on (owner-local); inside quiet hours only during `digest_hour` itself, so catch-up never runs in quiet hours. Paused, quiet or unpaired → `digest.deferred {date, reason}` once per date and reason. Build = one transaction under the agent row lock: render the undelivered items plus live sections, insert the date's row with a 2-minute send lease, tie the items to it (`digest_id`). Send the stored body; success → `sent` (+ items) and `digest.sent {date, items, leftOut}`; nothing to say → `empty`, `digest.empty`; retryable failure → the lease is kept until a backoff (1 min doubling to 15 min, at least `retryAfterMs`), one `digest.deferred send_failed {attempt, retryAt}` per attempt, retried with the same body; permanent failure, or a date that ends undelivered → `rolled_over`, items back to the pool for the next date (`digest.deferred day_ended|send_failed`). Before re-sending, a body the gateway already recorded is marked sent instead. Delivery is at least once only across a crash between the transport send and the gateway's record.
- *Rendering* (`render.ts`): `Today:`, then sections by `order`: `Messages taken` (`message_taken`), `Agent conversations` (`a2a_opened`, `a2a_closed`, `a2a_stalled`, raised by M4), `Drafts` (`draft_created`; its subject and addresses are model-written, so folded with `quoteFolded`), `Booked` (`booked`, `a2a_booked`), `Waiting for you` (live, added by `approvalsModule`: `listPending` — pending and unexpired — one line per approval, its stored prompt without ` Reply yes or no.`, `#ref` kept so the owner can name it: `yes 7` under the digest is not under the prompt, so Violet shows prompt #7 again (I19) and the yes or button under that answers it), `Also` (`approval_expired`, overflowed `now` flags, unknown kinds). One `- ` line per item (re-sanitized, I13), ≤ 10 per section then `+N more`, whole body ≤ 3500 chars cut on whole lines with `+N more not shown`; left-out items count as delivered. `app.digest`: `registerKind(kind, sectionKey)`, `addSection({key, title, order, lines?(agentId, range)})` (same key replaces; a live section that throws or does not answer within 5 s is logged and omitted; live sections run in parallel and `runDue` works on up to 4 agents at once, so one slow agent does not hold back the others), `runDue(now)`, `preview(agentId)` (writes nothing). A module that registers sections installs after `flagsModule`.
- *Conflict check* (`conflicts.ts`, `registerPerAgent('flags.conflicts', 1 h)`): `listEvents(now, now+36h)`; timed events only (all-day and zero-length never conflict; touching is not overlap; `CalendarEvent` has no free/cancelled marker and the real provider drops cancelled events); pairs ordered by overlap start; at most 3 new pairs per run; kind `calendar_conflict`, dedupe key `conflict:` + sorted `id@startISO` of both, so a moved event flags again. Text is one code-rendered line with quoted titles and today/tomorrow/weekday words in the owner's zone; in quiet hours it is worded for the 07:00 delivery and overlaps over by then are skipped. Any provider or delivery error → one log line (error class only), no flag, never thrown; `GoogleNotConfiguredError` → one line per run for all agents.
- Action names (I15): `flag.held`, `flag.released`, `flag.overflow`, `digest.sent`, `digest.empty`, `digest.deferred`.

### 8.6 Pause

`pause` → state flips at ingest (never behind the lane's backlog), one ack, then silence to everyone (I14). Because the gateway checks `paused` at send time, nothing an older job or its retry tries to send to the owner or a stranger gets out once the pause is ingested. Agent-to-agent messages do not go through the gateway: every transaction that writes one for the agent (Envoy act, open, guidance, owner close) reads the agent row `FOR SHARE` and refuses when paused, so a Brain or Envoy turn already running when the pause lands sends nothing to the other agent either; an accept by the other side skips the paused owner's free/busy (the booking guard checks it after both yeses). A booking is not claimed while either owner is paused: the second yes gets `Waiting for <first>.` (or, for the paused owner, that it waits for their resume), nothing is read or written, and the a2a `onResume` hook books it once, both owners told by notice. The pause is checked again right before each calendar write (`CalendarWriter`, F2; the guard checks it too, before and after its free/busy read): a pause that lands after the claim while nothing of the booking is written yet holds it the same way (the approvals stay `approved`); one that lands after a write fails the booking closed with the generic reason (`a calendar didn't accept it`) and undoes what was written, so nothing about the paused owner's calendar reaches the other side. A pause that lands after a crash between the two writes (or after an expiry of a held booking whose settle did not finish) is handled the same way: the retried hook or the booking sweep does not wait for the resume; it claims the booking even though an owner is paused, marks the yeses failed, undoes the other owner's events and settles it failed with the same lines, reading and writing nothing on the paused owner's calendar (the paused owner's line waits for the resume). If the half already written is on the paused owner's own calendar, it stays there and the booking waits for the resume, as when nothing is written. One window is left: a pause that lands while the call to Google is already in flight does not stop that write. A held booking is never closed by the idle sweep (F1); it ends in one of two ways, each with one code-written line to both owners (a paused owner's waits for the resume): the resume while every event still starts in the future books it as usual (guard, fresh free/busy, both calendars or neither), or the a2a sweep (every 10 min, also while paused) finds the first event's start passed (an agreement with no events: the later approval expiry) and settles it failed, nothing read or written: `Couldn't book …: the time came before it could be booked. Nothing was booked.` A solo `calendar_event` whose write a pause refused stays `approved` and is booked by the approvals `onResume` hook, which sends its usual line. Messages that arrive while paused stay held even if a `resume` is ingested before their job runs, and a job that recorded its `held` step stays held on retry after a resume (it only finishes its flag step). `resume` → ack, `onResume` hooks run: the a2a hooks first (releases approved before the pause, held bookings, then every waiting notice sent at once, in order; waiting Envoy turns are re-queued), then the approvals hook (held solo bookings, then the unsent approval prompts in creation order), so a waiting prompt is the last thing the owner gets (S3). Stranger messages taken while paused were stored with their `message_taken` digest flag (8.1 step 5) but got no canned reply; they appear in the first digest after resume (the digest is deferred while paused).
